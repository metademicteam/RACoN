Resource-Aware Collaborative Network

One request. Many PCs. One synthesized answer.

RACoN 1.2 gives every installation a Friend AI that runs on your own model and keeps working offline. Run the whole server as one Docker container with PostgreSQL, watch every worker and every routed request in the admin console, then switch Friend AI to network mode: the planner builds a validated task graph, compatible PCs execute it, and the synthesizer returns one answer with any gaps named.

What RACoN is

Agentic Task Center

A planner decomposes the request into a task DAG. Independent tasks run in parallel; dependent tasks wait for their inputs. A server-side synthesizer merges the results and names anything that could not be completed.

Hardware-matched models

RACoN measures RAM and GPU telemetry, ranks models that actually fit, and installs verified GGUF files from Hugging Face with SHA-256 validation. SmolLM2 360M, Qwen 2.5 0.5B and Llama 3.2 1B ship as one-click options.

Local-first desktop app

The local engine binds to loopback with a per-install token. Inference, the model manager, hardware telemetry and the Task Center all work without the public network. Ubuntu Server installs can run headless with racon --headless.

Honest by construction

Missing telemetry is reported as unavailable, not invented. Failed tasks become partial results with an explicit gap list. There is no simulated inference path in production code.

Friend AI is the interface

One conversation, two explicit modes. The mode actually used is always shown.

Local assistant

On-device streaming from your own GGUF model. It never claims that remote workers were used, and it keeps answering when the network or the coordinator is unavailable.

RACoN network mode

Submits a real orchestration job from the conversation. The reply shows the plan, each task's worker and state, retries, and the synthesized answer. Cancel from the same bubble.

Honest fallback

If no worker is reachable the job runs locally and records the mode. If planning cannot produce a valid task graph, one task executes the whole request and the reason is shown — never a fabricated decomposition.

How it works

  1. Install on each PC: the Windows installer or the Ubuntu tarball/.deb. Both install per-user and need no administrator rights.
  2. Set up Friend AI on first launch. RACoN measures RAM and GPU, recommends a verified GGUF that fits, and downloads it with live progress and a SHA-256 check.
  3. Join the cluster as a worker when you want to contribute capacity. Enrollment uses an Ed25519 identity; heartbeats report real CPU, RAM and active tasks.
  4. Ask Friend AI. Keep the request local, or switch to RACoN network mode: the planner builds a DAG, the selector places each task, and the synthesizer returns the final answer with any gaps named — in the same conversation.
  5. Call the OpenAI-compatible API at racon.metademic.org/v1 with an API key.

RACoN 1.2's local orchestration is verified end to end. The Docker server now exposes the worker ingress, desktop API, OpenAI surface and admin console from one process. When a small planner cannot produce a valid task graph, the job runs as one task and records why. RACoN never claims that multiple PCs pool RAM or VRAM.

One server. PostgreSQL. One admin console.

Unified Docker server

One container serves /enroll, /heartbeat, /tasks/*, /api/v1/*, /v1/* and /admin. Workers reach it over Tailscale, so no public port is required.

PostgreSQL state

Nodes, jobs, tasks and the routing audit are durable in PostgreSQL. The server image also ships a pinned llama.cpp build, so verified GGUF downloads are servable immediately.

Operator dashboard

See every worker with CPU, RAM, GPU/VRAM, OS, runtimes, served models and heartbeat age. Follow the live source → target request log. Inspect the agentic scheduler's jobs, tasks and assigned workers. Run diagnostics, preview the smart router, approve, revoke or dispatch a test task.

Each file is downloaded from Hugging Face over HTTPS and checked against the Hub's SHA-256 before it is installed. A Hugging Face token is optional and never stored in the app.

What's new in 1.2.0

  • Zero-setup connection — the Windows installer ships preconfigured with the RACoN server URL and token, so Friend AI connects on first launch without PowerShell, environment variables, or manual settings.
  • Streaming network answers — RACoN network jobs now stream the synthesized answer token by token and use the full 2048-token budget instead of truncating the result.
  • Scoped client token — the app no longer ships the server administrator token. A limited client token can run jobs and chat but cannot open the admin console or change server settings.
  • Real worker inventory — every node now reports its actual CPU, GPU, RAM, OS and runtimes, and the running desktop app enrolls itself as a provider so it appears in the admin console with a live heartbeat.
  • RACoN Network Gateway — one OpenAI-compatible endpoint with RACoN inference keys. model: "racon" streams a query from one worker, or plans a complex task, streams it across workers, and merges the answer. Tool calling and response_format work with agent harnesses.
  • Network fixed — the Docker server now exposes the worker ingress (/enroll, /heartbeat, /tasks/claim, /tasks/report) from the same app as the desktop API. Workers can finally join the container.
  • PostgreSQL — durable nodes, orchestration jobs, tasks and an append-only routing_events audit. SQLite remains the desktop/test store.
  • Admin console — a separate operator app at /admin with every worker's CPU, RAM, GPU/VRAM, OS, runtimes and heartbeat, the live node-to-node request log, the agentic scheduler's jobs and tasks, download progress and invites.
  • GGUF inference on the server — the server image ships a pinned llama.cpp build, so a verified Hugging Face GGUF downloads and serves without a host runtime. The container also supports RACON_RUNTIME=ollama.
  • Download reliability — resumable .part transfers, three automatic retries, size validation and SHA-256 verification before install.
  • Worker execution — a worker with only llama.cpp can complete distributed tasks; Ollama is tried first, then the local RACoN engine. Failures stay explicit.
  • Smart model router — model: "auto" classifies each request (code, reasoning, chat, tool, creative, image; quick/moderate/deep), applies hard capability filters, and selects a capable installed model. Every response carries the decision in racon.router; POST /api/v1/scheduler/route previews it.
  • Model-aware workers — enrollment advertises the models a worker can serve (signed only when present, so older agents still verify), the selector filters by model and capability, and a worker that misses the 30-second heartbeat window is excluded.
  • Operator diagnostics — the admin console's Diagnostics tab (and GET /api/v1/admin/diagnostics) checks PostgreSQL, the inference runtime, Ollama, llama.cpp, installed models, worker liveness, the routing log and token strength.
  • Windows and Linux 1.2.0 builds — refreshed installer, Ubuntu tarball and .deb, with published SHA-256 checksums.

Public API

One OpenAI-compatible endpoint for the whole network. Any agent harness works with a RACoN inference key.

curl https://desktop-b7l73cl.tail6cb521.ts.net/v1/chat/completions \
  -H "Authorization: Bearer rk_your_key" \
  -H "Content-Type: application/json" \
  -d '{"model":"racon","messages":[{"role":"user","content":"Compare CPU vs GPU inference."}],"stream":true}'
  • model: "racon" — a simple query streams from one worker; a complex task is planned, split across streaming workers, and the results are merged by the synthesizer.
  • racon-single, racon-task, and racon-task:<model> override the mode or pin a worker model.
  • OpenAI chat, SSE streaming, tool calling and response_format are supported. Tool requests always stay on one worker.
  • Auth: Authorization: Bearer rk_… or x-api-key. Keys are issued from the admin console; only SHA-256 digests are stored.
  • Limits: per-key rate limit (default 60/min), max_tokens up to 32768. Errors use the OpenAI envelope: 401 bad key, 403 wrong scope, 429 rate limit, 404 unknown model, 503 no worker.

Workers connect outbound to the coordinator, so they can be behind NAT. The coordinator is the discovery and scheduling point; it never exposes the administrator token to clients.

Public workloads may be visible to the operator of the machine that runs them. Do not send personal, confidential, medical, financial or credential data.
